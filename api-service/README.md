# API Service

BFF (Backend-for-Frontend) + API composition для Multi-Vendor Marketplace. Собирает данные из нескольких сервисов в один HTTP-ответ, сокращая число round-trip'ов с фронтенда. Не gateway и не auth-прокси: прямой доступ к каждому из 10 доменных сервисов остаётся официально поддерживаемым путём, `api-service` строго добавочный.

Без своей БД/схемы — каждый composed-эндпоинт читает уже существующие эндпоинты остальных сервисов через фасады (`src/facades/`) и форвардит `Authorization`-заголовок вызывающего как есть, никогда `SYSTEM_TOKEN` — downstream-авторизация (в т.ч. поресурсная проверка владения) работает ровно так же, как при прямом запросе.

Подробное обоснование архитектуры — `services/PLAN_api-service.md` в Obsidian vault проекта.

## Порт

`8100`

## Запуск

```bash
docker compose up -d
```

## API

| Метод | Путь | Описание |
|-------|------|----------|
| `GET` | `/health` | Агрегированный статус: свой + `catalog`/`order`/`payment`/`inventory` (только сервисы, реально используемые composed-эндпоинтами) |
| `GET` | `/storefront/products/{product_id}` | Карточка товара: каталог + актуальный остаток (не устаревшее поле `stock` каталога) |
| `GET` | `/orders/{order_id}/full` | Заказ + статус оплаты одним запросом |

Интерактивная документация (`/docs`, `/redoc`) доступна только здесь — на остальных 10 сервисах отключена (`docs_url=None`, `redoc_url=None`); их `/openapi.json` при этом продолжает отдаваться.

## Отказоустойчивость

Недоступность второстепенного downstream-сервиса не валит весь запрос — эндпоинт деградирует до `null` на соответствующем поле:
- `/storefront/products/{id}`: `inventory-service` недоступен → `available`/`warehouse_id`: `null`, карточка товара всё равно возвращается.
- `/orders/{id}/full`: `payment-service` недоступен → `payment`: `null`, данные заказа всё равно возвращаются.

Первичный источник данных эндпоинта (`catalog-service` для витрины, `order-service` для заказа) — не деградирует: его 404/недоступность приводит к ошибке всего запроса, поскольку без него нечего показывать.

`core/http_client.py` не повторяет запрос при 4xx-ответе (это осмысленный ответ сервера, а не временный сбой) — только при сетевых ошибках и 5xx.
